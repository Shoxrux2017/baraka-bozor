# Apple Stage 3 — Cart and the Card's Stepper Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A step on a cart line or a product card shows the new quantity at once and quick taps go to the server as one change; removing a line asks nothing, folds it away and offers «Вернуть»; a line can be swiped away; large text stacks the sum over the stepper instead of shrinking it; the totals and the address come before «Добавьте к заказу»; amounts stay the server's and change softly.

**Architecture:** One per-account `CartQuantityQueue` (Riverpod `Notifier`, cart `application/`) holds the quantities the Customer has set and the server has not answered, by product id. The card and the cart line show `wish ?? server quantity` and send through it: an add, an exact quantity, a removal and an undo go at once, steps 0.5 s after the last tap, and a product never has two requests on the way — the newest wish follows the answer. Requests still go through the existing `AddToCartController` and `CartLineController`, so `CartMutation`'s reload and account rules hold. Shared motion and feedback pieces (`Fold`, `FoldingColumn`, `SoftChange`, the undo bar, `announce`) are built in `core/` for the later stages.

**Tech Stack:** Flutter 3.47.5, flutter_riverpod 3.4.3, flutter_test (`tester.takeAnnouncements()`, `meetsGuideline(iOSTapTargetGuideline)`, `SystemChannels.platform` mock for haptics).

**Spec:** `tasks/APPLE_BATCH.md` stage 3 (items `cart-4`, `cart-5`, `cart-7`, `cart-8` **Owner**, `cart-9`, `cart-10`, `home-5`, `home-6`); the live tests «Тест корзины - Apple» and «Тест главной - Apple» (items 5, 6) in the Claude Design project "BarakaBozor — стиль покупателя" (local copy of the home test `G:\tools\tmp\w-home\site\home.html`); `DL-80` (2), `DL-85` (2), `DL-117` (9), `DL-118` (5); `frontend/AGENTS.md` §§ 5, 10, 11.

## Review Focus

1. Quick taps and then leaving within 500 ms: three «+» on a line and «Оформить», or the back button. Checkout must see 2,5, and a left screen must still send. Task 5 test (`Оформить` settles first) and Task 2 test (the send goes with no screen left).
2. A failure in the middle of a burst: the connection drops on the coalesced send. The card or the line goes back to the cart's quantity, one snackbar «Нет связи — в корзине осталось как было», nothing sent again. Task 2 and Task 3 tests.
3. «Вернуть» while the removal is still on its way, or tapped twice: the line comes back once, with its quantity, note and rule. Task 2 test (restore during the removal) and Task 4 test (note and rule kept, a second tap does nothing).
4. Another account within 500 ms of a step: a sign-out and a new sign-in send nothing for the old wish and show none of it. Task 2 test.
5. A drag that is really a scroll: a mostly vertical drag on a line scrolls the cart and never moves the row; a short slow drag left springs back. Task 4 tests.

### Task 2: The quantity queue

**Files:**
- Create: `frontend/lib/features/cart/application/cart_quantity_queue.dart`
- Test: `frontend/test/features/cart/application/cart_quantity_queue_test.dart` (`testWidgets` over a `ProviderContainer` as in `cart_controllers_test.dart`, so `tester.pump(duration)` drives the timers; the container's `cartProvider(account)` is listened to so answers land)

**Interfaces:**
- Consumes: `addToCartProvider(productId).notifier.add(NewCartLine)`, `cartLineProvider(lineId).notifier.change(CartLinePatch)` / `.remove()`, their `MutationState.failure` read right after the await; `currentCartProvider`; `customerAccountProvider`.
- Produces: `class CartQuantityQueue extends Notifier<Map<String, String>>` — state: product id → the quantity the Customer set and the server has not yet answered, `CartQuantityQueue.out` (`'0'`) for "out of the cart". `build()` watches `customerAccountProvider` and returns `{}`; `ref.onDispose` cancels every timer and completes every waiting caller with `null`.
  - `static const Duration settleDelay = Duration(milliseconds: 500);`
  - `Future<ApiFailure?> want(String productId, String quantity, {bool now = false})` — a step or an exact quantity (`now: true`); goes at once also when the product has no line in the cart.
  - `Future<ApiFailure?> remove(String productId)` — at once.
  - `Future<ApiFailure?> restore(NewCartLine line)` — at once; an add uses the line's note and rule.
  - `Future<bool> settle()` — sends every waiting step now and completes when every product is answered; `true` when nothing failed.
  - Each future completes with the failure of the request that carried that call's wish, or `null` on success, when a later call superseded it, or for `cart_item_already_exists` (the reloaded cart shows the line). `CancelledFailure` completes as `null`.
- Produces: `final NotifierProvider<CartQuantityQueue, Map<String, String>> cartQuantityQueueProvider` (not auto-disposed: a step outlives its screen).
- Produces: `String? shownCartQuantity(Map<String, String> wishes, String productId, CartLine? line)` — the wish, else `line?.quantity`; `null` for `out` or no line.

The send, per product (the one algorithm the signatures leave open):

```text
wish(id, q, now, template?):  complete the previous waiting caller of id with null; new caller
                              state[id] = q; keep template if given; cancel id's timer
                              now, or no line of id in the server cart ? send(id) : timer(settleDelay, send(id))
send(id):  if a request for id is on its way → return (its answer sends again)
           q = state[id]; none → return.  line = the server cart's line of id
           q == out && line == null       → done(id, null)
           q == out                       → remove(line.id)
           line == null                   → add(NewCartLine(id, q, template?.note, template?.rule ?? allowSimilar))
           same amount as line.quantity   → done(id, null)
           otherwise                      → change(line.id, CartLinePatch.between(line, quantity: q, note and rule unchanged))
answer:    the queue rebuilt meanwhile (another account) → ignore
           failed or no answer → drop state[id], timer and template; complete the newest caller of id with the failure
           state[id] == the quantity sent → done(id, null): drop the wish and template, complete the caller
           otherwise (a newer wish) → send(id) again at once unless its timer runs
```
