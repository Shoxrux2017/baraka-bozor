# Apple Stage 21 — «Удаление аккаунта» Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Account deletion as the test draws it: a sheet that says at once «Это навсегда — вернуть аккаунт нельзя.», shows what is erased and what stays as two grey groups with icons and the true words about orders (the Owner's item), asks «Получить код для удаления» over a bold «Оставить аккаунт» with «Код для удаления придёт в Telegram на …», drags like any sheet but holds while the code is sent, says «Отправляем код…» and lets the Customer leave, shows «Нет связи — код не отправлен · Повторить», and turns in place into «Сейчас удалить нельзя» with the order's card; a code screen with green boxes, the sign-in code pieces but no auto-delete, a grey button that says what is missing and turns red on six digits, «Удаляем аккаунт…», a lost answer that checks itself («Проверяем…») and ends on «Аккаунт удалён», an offline strip that keeps the code; a calm done screen that fades in with a grey check, a success buzz and the true text (the Owner's item). The server spends the code only under the erasure's locks, so a racing order can no longer burn it.

**Architecture:** Server: `EraseCustomer::erase` takes an optional consent closure that runs under the cart and user locks after the unfinished-order check; the deletion controller passes the code check as that closure, and a refused code is rethrown after the commit so its count persists. The `409` names the order's status and item count. Client: the interceptor gains a per-request "keep the session on `authentication_required`" option, so the deletion's own calls read a `401` as "the account is gone" instead of dropping to «Вход»; `AccountDeletionController` takes the sign-in controller's shape (running/failed action, wrong code, tries left, misses) plus a `check` step after a lost answer and a `forgetAccount` clean-up; the sheet becomes one widget with two faces; the code screen reuses `CodeBoxes`, `LockCard`, the paste chip, «Открыть Telegram» and the «Не пришёл код?» sheet body; the done route fades.

**Tech Stack:** Laravel 13 + PostgreSQL (feature tests, model events for the race); Flutter 3.47.5, flutter_riverpod 3.4.3, go_router 18 (`CustomTransitionPage`); core `SubmitButton`, `RetryStrip`, `announce`, `textScaleAt`; auth `CodeBoxes`, `LockCard`, `RiseIn`, `ClipboardCode`, `TelegramLauncher`, `AuthNotice`; flutter_test (`takeAnnouncements`, `meetsGuideline(iOSTapTargetGuideline)`, `NonlinearTextScaler`, `SystemChannels.platform` mock for haptics). No new package.

## Global Constraints

- Changes stay in `backend/`, `frontend/`, `docs/` and `tasks/`. No migration, no new package. Generated localizations come from `flutter gen-l10n`, never by hand.
- **Server** (`AGENTS.md` §5, §6): the code is checked only after the cart lock, the user-row lock and the unfinished-order check, inside the erasure's transaction; a refused code (wrong, expired, exhausted, missing, locked) commits its count and erases nothing; the third wrong code still answers `429 code_locked` and locks the phone. Nothing new is stored or logged. The `409 account_has_unfinished_orders` details become exactly `{order_id, order_number, status, item_count}` everywhere it is thrown (deletion code, deletion, Admin erasure); `item_count` counts the lines the way the Customer's order list does (`OrderLineSums::add`).
- **Session rule:** only the deletion's two calls (`POST /customer/account/delete`, the check `GET /customer/profile`) keep the session on `401 authentication_required`; for them that answer means the account is gone. `401 account_blocked` drops the session as everywhere. Every other request is unchanged.
- **Flow rules.** The sheet requests the code at once; while it runs, «Оставить аккаунт», the scrim and back close the sheet and the answer is dropped (`reset`), but a drag only rubber-bands. A `409` turns the same sheet into the blocked face (no second sheet). The sixth digit never deletes; only «Удалить аккаунт» (or the keyboard's done key) does. Back is blocked while deleting or checking. A deletion — a `204`, or a `401 authentication_required` from the delete or the check — goes to `/account-deleted` first, then forgets the account on the device and drops the Customer session.
- **Haptics:** `HapticFeedback.errorNotification` on a wrong code; `HapticFeedback.successNotification` once when the account is deleted. Nothing else buzzes.

## Review Focus

1. A sheet closed while its code request runs, then opened again at once: the first answer neither opens the code screen nor turns the new sheet into the blocked face; the new request runs normally. Task 3 test `'reset drops a request in flight'`, Task 5 test `'a late answer of a closed sheet changes nothing'`.
2. A lost delete answer while the account still exists: «Нет связи — аккаунт не удалён», the six digits stay, «Повторить» sends exactly one delete with the same code; a retry answered `401` is a deletion. Task 3 test `'a retry answered 401 is a deletion'`, Task 6 test `'Повторить after a lost answer deletes once with the kept code'`.
3. A deletion read from a `401` never shows «Вход» first: the location goes from the code screen straight to `/account-deleted`, and the session is dropped after. Task 6 test `'a deletion read from a 401 lands on Аккаунт удалён, not on Вход'`.
4. Server: wrong codes checked inside the erasure's transaction keep their count; the third one answers `429 code_locked` and locks sign-in too. Task 1 test `test_wrong_codes_still_lock_after_three`.
5. While «Отправляем код…»: a drag never closes the sheet, but «Оставить аккаунт», the scrim and back do, and the answer then changes nothing. Task 5 test `'while sending a drag springs back but Оставить аккаунт leaves'`.
