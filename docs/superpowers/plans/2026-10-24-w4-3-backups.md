# W4-3 — Backups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task (one `plan-implementer` per task, the lead checks each diff). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every night at 03:00 Tashkent the production stack copies its database and its product images, encrypted, into a restic repository off the host; each run records its outcome; and one script restores a chosen copy into an empty stack, proven by a backup-wipe-restore cycle that runs in CI and on the development machine.

**Architecture:** A `backup` service of its own in `docker/compose.prod.yaml`, behind the Compose profile `backup`, so the production stack runs it and a scratch stack for a restore never does. Its image (Alpine with `pg_dump` 17, restic and supercronic) dumps the database as a read-only role, takes one restic snapshot of the dump and the images volume, prunes by 7/4/6, checks the repository weekly and writes its outcome to a status volume. `docker/backup/restore.sh`, run on the host, refuses any stack whose database already has tables, restores the dump in one transaction through the `db` container and the images through the `app` container as `www-data`, then migrates and starts the stack.

**Tech Stack:** Docker Compose v2 profiles, `alpine:3.24` with `postgresql17-client`, `restic` 0.18, `supercronic` 0.2, `tzdata` (all from Alpine's repositories), POSIX `sh` inside the container, `bash` on the host.

**Spec:** `tasks/WAVE_4.md` task note W4-3; `docs/DECISIONS.md` `DL-104` (6), `DL-107`; `docs/07-architecture.md` section 34. Finer decisions go into `DL-109` (Task 3 carries its points).

## Review Focus

1. **A job started by supercronic, not by hand.** The tests run `backup.sh` through `docker compose exec`; the night runs it from supercronic, whose environment and time zone could differ. Task 1 Step 5 (`supercronic -test`, next run printed as 03:00 +05), Task 4 Step 4 (a scheduled run fires and writes the status).
2. **A night that half-fails must never look like success.** A dump that fails, a repository that refuses, a prune that fails: each leaves `result: failure` with its step, a non-zero exit, no ping, and no dump file behind. Task 1 Step 1 (`dump` and `backup` failures; the snapshot count does not grow on a dump failure).
3. **The role can read everything and write nothing.** `pg_dump` as `barakabozor_backup` must cover every table, and the role must be refused a write. Task 1 Step 1 (`create table` refused), Task 2 Step 1 (the full-content fingerprint matches after the restore).
4. **A restore aimed at a live stack.** It must stop before touching anything. Task 2 Step 1 (a second restore into the restored stack exits non-zero with "not empty", fingerprint unchanged).
5. **Restored images the app cannot replace.** Files must come back owned by `www-data` so an Admin's next upload can delete the old one. Task 2 Step 1 (owner and sha256 of the marker image).

- [ ] **Step 3: Implement `restore.sh`.** Order:
  1. `up -d --wait db`.
  2. Refuse with `restore.sh: the database of <project> is not empty; restore only into a new stack` (exit 1) when `pg_tables` lists any table in `public` (queried in the `db` container as `$POSTGRES_USER`).
  3. The database: `run --rm --no-deps -T backup restic dump <id> /backup/db/barakabozor.dump` piped into `exec -T db sh -c` that writes stdin to a `mktemp` file, runs `pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --no-privileges --single-transaction --exit-on-error`, removes the file, and keeps the exit code. A file, not stdin, because a custom-format archive read from a pipe cannot seek.

  6. Last line `restore.sh: snapshot <id> restored into <project>`.
  A header comment says: only into an empty stack; the `backup` role is cluster-wide and not in the dump, so a production stack restored from scratch runs `create-role.sh` again.
