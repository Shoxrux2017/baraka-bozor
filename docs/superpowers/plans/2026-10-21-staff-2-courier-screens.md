# Staff Stage 2 — The Courier's Screens Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Courier's area looks and works like the approved drawings 48–54 of `kit/09-kurer.dc.html`: a kit list of deliveries, a delivery page per state with a status card, call cards, the address and the payment, a pinned footer with the next step, kit sheets for "Доставлено" and "Не доставлено", and a kit "no longer yours" screen.

**Architecture:** Client only. The pieces the Shopper's stage built privately and the Courier needs too — the status card, the steps, the segment bar, the call card, the footer, the price and note fields — move into `core/widgets/kit/`, and the Shopper's screens use them unchanged in look. `features/courier/presentation` is rebuilt from focused files. The controllers, the keyed handover, the 10-second refresh and every server rule stay as they are; the only data change is reading whether the server runs with a handoff point, which it already says by sending or not sending `shopper_phone`.

**Tech Stack:** Flutter 3.47.5, Riverpod 3, go_router, `flutter gen-l10n` (template `app_uz.arb`), Montserrat, `KitColors`.

**Spec:** `kit/09-kurer.dc.html` in the Claude Design project "BarakaBozor — стиль покупателя", approved by the Owner on 2026-10-21 ("да"). Frames: 48 мои доставки, 48а доставок нет, 49 новая доставка (with a handoff point), 49а принята (without one), 49б клиент просит отменить, 50 в пути (cash), 50а в пути (online), 51 доставлено: наличные, 51а сумма не совпадает, 51б доставлено: онлайн, 51в ответа нет, 52 не доставлено, 52а другая причина, 53 доставка закрыта (list + message), 54 доставка больше не ваша. The Owner's rule is `DL-97`; the agent's rules are `DL-99`, one item per task. The stage-1 plan `docs/superpowers/plans/2026-10-21-staff-1-shopper-screens.md` shows the kit pieces this plan reuses.

## Review Focus

1. **A sheet closed while its outcome runs.** "Доставлено" and "Не доставлено" each run a request; while it runs the sheet cannot be closed (back, the scrim, the round ×) and its buttons hold, so the answer lands on a sheet that still shows. Task 4 test: "a running handover holds its sheet".
2. **A handover without a sure answer.** After a lost answer the page offers only the handover again — "Не доставлено" is gone, since the order may already be completed — and the sheet sends the same cash, locked, under the same key; when the delivery can no longer be read, the resend still stands. Task 3 tests "after a lost answer only the handover goes again", "a lost answer whose delivery can no longer be read offers the handover again"; Task 4 test "the resent handover locks the cash it sent".
3. **A cancellation request.** While it waits, the status card says not to set off and the footer's start is held with why; once an Operator decides, nothing stale stays. Task 3 tests (rewritten): "a cancellation request waiting keeps the Courier from setting off, and says why", "once the request is decided, nothing tells the Courier to wait".
4. **A delivery at the extremes.** A 300-character note to the Courier, a 255-character landmark, a long street and apartment, a 160-character wish, 99 999 999 сум, at 320×640 with text ×2 in both languages: nothing overflows and the footer stays reachable. Task 3 test: "the delivery holds at the extremes".
5. **Where the package is picked up.** The server sends no `shopper_phone` with a handoff point, `null` without one when no Shopper is named, a phone otherwise; the page says the package waits at the point, or to take it from the Shopper (with the call card only when a phone came). Task 3 test: "the pickup says where the package waits"; Task 3 API test "the handoff point follows whether the Shopper's phone is sent".
