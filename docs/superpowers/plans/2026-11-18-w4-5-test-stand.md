# W4-5 Step 1 — the test stand — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Everything the agent needs to put the backend, the worker, the scheduler and the web panel on a fresh AWS Lightsail server as a test stand for two or three acquaintances, and to deploy and roll back later releases there with one command.

**Architecture:** W4-2 built the production stack (`docker/compose.prod.yaml`) and W4-3 the backups. This task adds: a `staging` environment that keeps every production boot check except two (test phones with a secret code, the fake code driver); a maintenance answer in Caddy; `docker/deploy.sh` that deploys a git tag from `main` and rolls back; `docker/server/prepare.sh` for the fresh server; the runbook `docker/DEPLOY.md`; and two Windows scripts that build the tester APK and publish the panel. After the merge the lead runs the stand live (last section).

**Tech Stack:** Laravel 13 / PHP 8.4, PostgreSQL 17, Docker Compose, Caddy 2.11, bash, PowerShell 5.1, Flutter.

**Spec:** `tasks/WAVE_4.md` (W4-5 notes), `docs/DECISIONS.md` `DL-104` (6)–(7), `DL-107`, `DL-109`, `DL-110`, and the Owner's decision of 2026-11-18 recorded by Task 1 as `DL-141`.

## Global Constraints

- No secret value ever reaches output, a log, an exception message or a commit: scripts print names, never values (`AGENTS.md` §5).
- No dependency change except Task 2's Symfony update, with the reason in its commit message (`AGENTS.md` §7).
- Never run `migrate:fresh`, `db:wipe` or any destructive artisan command against the development database; backend tests run only through the command in `docker/README.md`, "Run the test suite".
- Scratch stacks use their own Compose project names (`bb-deploy-test`) and ports; no container or volume of another project is touched (`AGENTS.md` §11).
- Bash scripts: `#!/usr/bin/env bash`, `set -euo pipefail`, `export MSYS_NO_PATHCONV=1` (they also run under Git Bash), messages prefixed with the script's name.
- Release tags match `^r[0-9]{4}\.[0-9]{2}\.[0-9]{2}\.[0-9]+$` (e.g. `r2026.11.19.1`) and must be ancestors of `origin/main`.
- Server layout (`BB_HOME`, default `/opt/barakabozor`): `repo/` (the clone), `stack.env`, `backup.env`, `state/` (`release`, `release.previous`, `deploy.log`), `dumps/`, `maintenance/`, `panel/releases/`, `panel/current` (relative link), `backup-repo/`.
- Every commit ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; messages name `DL-141`.
- Each task updates the documents its change touches in the same commit (`AGENTS.md` §3).

## Review Focus

1. **An SSH drop in the middle of a deploy.** The person expects the deploy to finish or stop at a step the log names. `deploy.sh` ignores `HUP` and mirrors its output to `state/deploy.log` with `tee --output-error=warn`; Task 4's test runs it with stdout closed.
2. **A failed migration.** The person expects the API to keep answering `503` (never a half-migrated app), the state files unchanged, and the message to name the dump and `--rollback`. Task 4's test deploys a tag with a broken migration.
3. **A build or Caddyfile failure before maintenance.** The person expects the running release to be untouched and the clone back on it. Task 4's test deploys a tag whose Caddyfile is invalid.
4. **A stale or failed backup at deploy time.** The person expects a warning naming the age, never a failed deploy. Task 4's test covers "no status yet" and a `failure` status.
5. **The test code on a public repository.** A guessable or development code on the stand is a login for anyone who reads the repository. Task 3's test refuses a guessable code in staging.
