# BarakaBozor — Open Specification Decisions

## Purpose

The locked `docs/01–09` passed cross-document audit on 2026-09-07. A second read on 2026-09-21 found questions the specification does not answer, or answers in two incompatible ways. None of them contradicts the business model; each is a decision that has not been made yet.

This file is the register. Each entry is resolved with the Project Owner **at its wave planning gate, before the first task that depends on it**, and is then frozen for that wave. Meeting one of these mid-implementation is a stop-and-ask condition, not a judgement call.

The assignment rule: **a decision belongs to the earliest wave whose schema task or public contract depends on it.** A decision that shapes a column or a constraint belongs to the wave that creates that table, even when the feature using it arrives later.

Resolving an entry means: decide, update every affected locked document, append an `AUD-` entry to `docs/CONTRACT_ALIGNMENT_REPORT.md`, then mark the row `Resolved` here with the date.

Status values: `Open`, `Resolved`, `Withdrawn`.

## Wave 0 — Foundation

| ID | Status | Blocks | Question |
|---|---|---|---|
| S-1 | **Resolved 2026-09-21** | `W0-BE-011` | **Role immutability versus unique phone.** `02` §3 and `BR-ROLE-002` say a role change means blocking the old account and creating a new one. `08` §3 makes `phone` plainly unique, and the same person keeps the same phone, so the second account cannot exist. Options: partial unique index over active accounts, with login resolving the active row; a phone-release rule applied on block; or accept that a role change requires a different phone. Affects `02`, `05`, `08`. |
| S-2 | **Resolved 2026-09-21** | `S01-FE-001` | **What "Desktop" means.** `02` §10 gives Operator, Admin and Manager a Desktop surface. No document says whether that is Flutter Web or a native desktop build. This decides the build targets, the Phase 2 "required target build", CORS configuration, and whether Sanctum runs in bearer-token or SPA-cookie mode. The mobile platform set needs the same answer; note that iOS release builds require macOS, and iOS push additionally requires an Apple Developer Program membership and an APNs key. Affects `02`, `07`, and the Wave 0 index. |
| S-3 | **Resolved 2026-09-22** | `W0-BE-012`, `S01-FE-002`, `S01-FE-003`, `S01-FE-004` | **Locale and message language.** `frontend/AGENTS.md` §8 separates machine values from localized labels, and API `message` is human-readable, but no document fixes the MVP language set (uz / ru / en), `Accept-Language` handling, or which language backend messages use. Affects `07`, `09`. |
| S-4 | **Resolved 2026-09-22** | `S01-BE-003` | **Staff login hardening and token lifetime.** `09` §6 fixes the OTP policy precisely. `09` §8 staff login has no rate limit and no lockout. Sanctum token expiry, maximum tokens per user, and the mechanics of revoking tokens when an account is blocked (`02` §12) are unspecified. Affects `07` §8, `09` §8–§11. |
| S-5 | **Resolved 2026-09-22** | `S01-BE-004` | **OTP verify "ensures one active Cart".** `04` §2 step 7 and `09` §7 make Cart creation part of verify, but Cart is a Wave 2 table, so a Wave 0 task cannot do it. Decide whether Wave 0 omits the step and Wave 2 retrofits it, or whether Carts are instead created lazily on first Cart access. Affects `04`, `09`, and the Wave 0 acceptance map. |
| S-16 | **Resolved 2026-09-22** | `S01-BE-003`, `W0-BE-012`, `S01-FE-002` | **Machine codes missing for `400`, `502` and `503`.** `09` §3 assigns HTTP `400` to a malformed protocol request and `502`/`503` to an external provider problem, but §54–§59 define no stable `code` for any of them, so a client cannot branch on them. `AUD-019` closed the same gap for `500` only. `400` becomes reachable with the first real request body; `502`/`503` with the first provider call. Until it is resolved, `S01-BE-001` renders any unmapped client error as a scope-safe `404 resource_not_found` and any unmapped server error with `server_error`. |
| S-17 | **Resolved 2026-09-22** | `W0-BE-012`, `S01-FE-002` | **`request_id` is in the locked envelope but nothing emits it.** `09` §3 defines the error envelope as four keys including `request_id`. `S01-BE-001` emits the other three; adding the fourth needs a correlation-ID source, and no document says where one comes from or whether it is required. Under `D-9` the shared error fixtures cannot be written while a declared envelope key has no defined source, so this now blocks the frontend track, not only error reporting. |

| S-19 | **Resolved 2026-09-22** | `W0-BE-011`, `S01-BE-004` | **Customer OTP verify when the only Customer account is blocked.** `09` §7 says verify "resolves or creates" the Customer account. After `AUD-023` the active-Customer index permits a blocked Customer row and an active Customer row on one phone, so when the only Customer row is blocked the contract allows both readings: resolve the blocked row, or create a new active one and thereby void the block. Plain phone uniqueness previously made the question unreachable. Opened by the independent review of `AUD-023`. |
| S-28 | **Resolved 2026-09-22** | `S01-BE-004` | **Does the staff-login rate limit extend to `/auth/change-password`?** `AUD-024` placed 5-per-phone and 20-per-IP per minute on `09` §8 only. §10 `change-password` verifies `current_password` and carries no limit, so a stolen token can be used to guess the password it protects without any bound. The caller is already authenticated, which lowers the risk but does not remove it. Opened by the independent review of `AUD-024`. |

## Wave 1 — Catalog and Account

| ID | Status | Blocks | Question |
|---|---|---|---|
| S-21 | Open | Wave 1 Catalog schema task | **Are both catalog languages required, or may one be empty?** `08` §6 and §7 now carry `name_uz` and `name_ru`. Requiring both doubles the Admin's data entry for every Product; allowing one empty means a Customer sometimes sees the other language or nothing. Opened by `AUD-024`. |
| S-22 | Open | Wave 1 Customer Catalog task | **What does a Customer see when their language's value is empty?** Fall back to the other language, or hide the Product? Hiding makes the catalog differ by language, which then differs by Order. Depends on `S-21`. Opened by `AUD-024`. |
| S-23 | Open | Wave 1 Catalog search task | **Does Customer search match across both languages or only the active one?** A Customer typing a Russian word for a Product whose `name_ru` is empty otherwise finds nothing. `08` §6 and §7 both index both name columns, so either answer is implementable. Opened by `AUD-024`. |
| S-25 | Open | Wave 1 Catalog schema task | **How is a bilingual catalog value stored?** `AUD-024` wrote paired columns (`name_uz`, `name_ru`) into `08` §6 and §7. That representation is the implementing agent's choice, not the Project Owner's decision, and root `AGENTS.md` §3 reserves database/schema contracts. The alternatives are a JSONB map per field or a `translations` table; the choice decides whether a third language is later a migration of every catalog table and index. **`08` currently states the paired-column form and needs sign-off or replacement before the Wave 1 schema task.** Opened by the independent review of `AUD-024`. |
| S-26 | Open | Wave 1 Catalog API task, `W0-BE-012` | **Does the Catalog API carry both languages?** `09` §14 Customer Catalog and §15 Admin Catalog were not amended for the bilingual change. Because `07` §30 forbids the server choosing a language, the client must receive both to select one — but that is not stated, and nothing says whether Admin write accepts both. This is API semantics, reserved under `AGENTS.md` §3, and not derivable from `S-21` or `S-22`. Opened by the independent review of `AUD-024`. |
| S-27 | Open | Wave 1 Customer profile or settings task | **How does a Customer choose their language?** `AUD-024` fixed the set to Uzbek and Russian but not the mechanism: device locale or an explicit switch, what the default is, and whether the choice is persisted. `03` has no language feature, `07` §27's feature list has no settings feature, `08` persists no preference, and `06` lists it in no wave, so the mechanism has no home today. Opened by the independent review of `AUD-024`. |
| S-29 | Open | Wave 1 Staff administration task | **Password strength and failed-attempt alerting.** `AUD-024` accepted no account lockout, for a sound reason. The residual it leaves: 5 attempts per phone per minute is 7,200 per day indefinitely against any known Staff phone, `09` §10 sets only a length rule (10–128), and `01`—`09` contain no complexity rule, no breach-list check, no failed-attempt notification and no alerting. Decide whether the MVP adds any of them. Opened by the independent review of `AUD-024`. |
| S-15 | Open | Catalog image delivery | **Product image delivery to the client.** `07` §10 covers storage. How Flutter fetches the bytes (public disk URL, signed URL, or an API endpoint) is unspecified, and it affects whether images are protected. |

| S-20 | Open | Wave 1 Staff administration task | **What `activate` returns when the new index rejects at write time.** `08` §3 states that Staff creation validates the phone so a duplicate returns `422 validation_failed` rather than a constraint violation. Nothing states whether `activate` validates then writes, or maps a constraint violation, nor what two racing activations return. `AGENTS.md` §3 reserves concurrency and replay policy, so this is a deliberate deferral rather than a gap. Opened by the independent review of `AUD-023`. |

## Wave 2 — Cart, Order and Money

Every entry here shapes a table or a public contract the Wave 2 schema task creates, even where the feature consuming it lands in Wave 3.

| ID | Status | Blocks | Question |
|---|---|---|---|
| S-24 | Open | Wave 2 Order snapshot task | **Which catalog name enters the historical Order snapshot?** `08` §13 requires persisting the original Product name at Order creation so historical Orders stay stable, and there are now two. Store both, or the one the Customer was using? This touches historical integrity under root `AGENTS.md` §7, and a wrong choice is not cheaply reversible once Orders exist. Assigned to Wave 2 because the snapshot is created there. Opened by `AUD-024`. |
| S-30 | Open | Wave 2 payment endpoint task | **Which code does an unreachable payment provider return?** `AUD-024` added `provider_unavailable` to `09` §54 for every `502`/`503`, while §58 already carried `payment_provider_unavailable`. A failing Payme call now matches both and nothing says which is returned, so a client cannot branch reliably. Opened by the independent review of `AUD-024`. |
| S-31 | Open | Wave 2 Cart or Order error task | **Where does a value a message would need travel in the error envelope?** `AUD-024` requires such a value to reach the client as data rather than inside prose, but `09` §3's envelope has four keys and `errors` is the validation channel every non-validation code leaves empty. The first MVP error that needs one — a minimum order amount is the example the record uses — is a Wave 2 error, so the slot is decided there. Opened by the independent review of `AUD-024`. |
| S-9 | Open | Wave 2 schema task | **Enum-like columns with no vocabulary.** `substitution_resolution`, `removed_reason_code`, `order_status_history.reason_code`, assignment `ended_reason`, and refund `reason_code` have no allowed values. Separately, "compatible unit semantics" for a replacement (`01` §10, `03` §13) is never defined; identical `unit_code` is the obvious reading but is not stated. Assigned to Wave 2 because the Order, assignment and refund tables are created there; the substitution values are consumed in Wave 3. |
| S-10 | Open | Wave 2 schema task | **"Unknown" payment outcome has no persisted form.** `payment_outcome_unknown` and the reconciliation rules treat it as a real state, but `payment_attempts.status` allows only `pending`, `successful`, `failed`, `cancelled`. Either define the derivation (pending plus age, or `last_reconciled_at`) or add a state. |
| S-11 | Open | Order idempotency task | **`IdempotencyStore` crash recovery.** A retry arriving while a row is stuck in `processing` could conflict, wait, or resume. `07` §17 and `08` §28 do not say which, and a crashed request leaves exactly that row. |
| S-13 | Open | Wave 2 schema task | **Price correction must mutate an unpaid obligation.** An Admin correction before the final payment lock (`BR-PRICE-006`, `09` §47) changes `final_total_uzs`, so an unpaid `final` or `additional` payment's `amount_uzs` must change with it. No document specifies mutating a payment obligation. Assigned to Wave 2 because it decides whether a payment obligation's amount is mutable at all; the Admin correction feature itself is Wave 3. |
| S-14 | Open | Cart task | **Cart status `abandoned` is never produced.** `08` §9 defines it; no rule in `03`, `04` or `05` creates it. Either define the transition or drop the value. Assigned to Wave 2 because Cart is created there. |

| S-18 | Open | Wave 2 assignment abstraction | **May a Shopper or Courier be assigned to an Order placed by a Customer account that shares their phone?** `AUD-023` permits one person to hold an active Staff account and an active Customer account on one number, so the same human can now stand on both sides of one Order: propose a substitution or a quantity change as the Shopper and grant the Customer Approval for it, making the financial consent `AGENTS.md` §7 protects self-granted. Plain phone uniqueness made this impossible before the amendment, so no rule addresses it. Decide whether assignment must exclude a Customer account sharing the assignee's phone, or whether it is accepted operationally with an audit trail. Opened by the independent review of `AUD-023`. |
